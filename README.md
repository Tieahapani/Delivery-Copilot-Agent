# Same Day Delivery Exception & Reroute Copilot

An agentic system that processes delivery exceptions in real time, triages them by urgency, computes alternate routes using real street data, and notifies customers, all with human dispatcher oversight through a live dashboard.

## Problem

Same day delivery networks generate hundreds of exceptions daily: wrong addresses, traffic delays, vehicle breakdowns, weather disruptions. Human dispatchers cannot scale to handle each one manually during peak hours. This system automates the routine 80% while surfacing the complex 20% to a dispatcher with a recommended action already attached.

## Architecture Overview

```
event_producer.py → Redis Stream → Dashboard Backend (consumes) → LangGraph graph.invoke() → WebSocket → Browser
                                          ↓
                                triage(LLM) → router → reroute(OSRM)/escalate → comms(LLM) → resolve
```

The pipeline is built as a LangGraph state graph with five nodes. Each event flows through triage (LLM classifies urgency and decides auto resolve or escalate), then either a reroute path (computes alternate driving routes via OSRM) or an escalation path (builds a dispatcher queue entry with recommended action). Both paths merge into a comms node (LLM drafts a customer notification) and a resolve node (logs the outcome for observability).

Redis Streams acts as the event buffer between the delivery network and the agent pipeline, ensuring exceptions are processed in order, never duplicated across workers, and never lost if the system restarts. The dashboard backend runs a background consumer loop that reads from the `delivery:exceptions` stream, processes each event through the full LangGraph graph, and pushes results to all connected browsers via WebSocket.

## Data: What Is Real and What Is Synthetic

One of the core design goals was grounding the simulation in real geography so that every route, distance, and driving time reflects actual San Francisco streets.

**Real data sources:**

| Source | What it provides |
|---|---|
| DataSF Registered Business Locations | 161,000+ SF business addresses with geocoded lat/lon coordinates |
| OpenStreetMap (BBBike SF extract) | Complete street network for San Francisco including speed limits, one way streets, and turn restrictions |
| OSRM (Open Source Routing Machine) | Driving time and distance computed on the real street graph, not straight line estimates |

**Synthetic data (generated by the manifest script):**

| Component | How it is generated |
|---|---|
| Driver assignments | K Means clustering on lat/lon groups nearby addresses into routes |
| Route sequencing | Nearest neighbor algorithm orders stops from a Bayview warehouse hub |
| Package priorities | Randomly assigned: 60% standard, 30% priority, 10% medical |
| SLA deadlines | Calculated from dispatch time: medical 2 hours, priority 3 hours, standard 4 hours |
| Exceptions | Probabilistically injected: 15% address issues, 10% traffic, 10% customer absent, 5% weather, 3% misloaded, 2% breakdown |

The manifest generator queries OSRM for each consecutive pair of stops, so every ETA accumulates real driving time plus 3 minutes of service time per stop.

## Rerouting: Production Pattern

For traffic delays, the reroute agent uses a production pattern rather than a simulation shortcut:

1. Query OSRM for 3 alternative routes with full geometry (`?alternatives=3&geometries=geojson`)
2. Build a circular buffer around the blocked location using Shapely (200m radius, properly converted from meters to degrees at SF's latitude)
3. Check each route's LineString geometry for intersection with the blocked zone
4. Pick the fastest route that avoids the blockage
5. If all routes pass through, select the one with the fewest exposure points and flag it for manual review

For address issues, the system defers the delivery to the end of the route and estimates a retry time. For customer absent, it marks the delivery as pending retry with no fake ETA since the retry depends on customer availability.

## Triage Agent: LLM Decision Making

The triage node sends the exception context to Claude (via LangChain) with a structured system prompt defining three urgency levels (HIGH, MEDIUM, LOW) and two decision paths (auto_resolve, escalate).

Key rules embedded in the prompt:

| Condition | Decision |
|---|---|
| Vehicle breakdown | Always escalate (requires physical backup driver) |
| Medical package with < 60 min to SLA | Escalate (too risky for autonomous handling) |
| Any exception with < 30 min to SLA | Escalate (no margin for error) |
| Bridge or highway closure with 5+ remaining stops | Escalate (no alternate routes, cascade risk) |
| Misloaded package | Escalate (requires hub coordination) |
| Weather disruption | Escalate (affects multiple drivers, needs fleet coordination) |
| Traffic on surface streets with 2+ hours buffer | Auto resolve via OSRM reroute |
| Address issues with time remaining | Auto resolve (contact customer) |

When SLA or ETA data is missing, the system sets time to SLA as negative and includes a note that negative values mean unknown or overdue. This prevents the LLM from treating missing data as "plenty of time" and forces cautious escalation.

## Evaluation: Golden Dataset and Scorecard

27 handcrafted test cases cover four categories, each with an input event and expected ground truth labels for urgency, decision, and notification channel.

| Category | Count | What it tests |
|---|---|---|
| Clear auto resolve | 8 | Standard packages with ample SLA buffer, solvable exceptions |
| Clear escalate | 8 | Medical packages, tight SLAs, breakdowns, weather, misloaded packages |
| Edge cases | 8 | Boundary decisions: medical with 55 min buffer, bridge closure with 10 stops, exactly 30 min to SLA |
| Invalid data | 3 | Missing SLA/ETA fields, nonsense coordinates, empty exception details |

**Scorecard (Claude Haiku 4.5):**

```
Decision accuracy:   25/27 (92.6%)
Urgency accuracy:    25/27 (92.6%)
Channel accuracy:    25/27 (92.6%)
JSON parse failures: 0/27
Average latency:     2.9s per event
```

The two misses were both edge cases where the LLM classified one urgency level differently than our ground truth. After reviewing the LLM's reasoning, we updated the ground truth labels in cases where the LLM's assessment was more defensible than ours. This iterative process of running evals, reviewing disagreements, and deciding whether to fix the label or the prompt is the standard workflow for production LLM evaluation.

## Live Dispatcher Dashboard

The dashboard is a FastAPI backend serving a single HTML page with WebSocket for real time updates and Leaflet.js for the map.

**Four panels:**

**Top bar** shows fleet health at a glance: active drivers, total deliveries, exception count, SLA compliance rate, auto resolved count, pending escalations, and average resolution time.

**Left panel** is the escalation queue sorted by urgency. Each card shows the delivery ID, driver, exception type, package priority, time to SLA, the LLM's triage reasoning, and a recommended action. Dispatchers click Approve or Dismiss to clear items.

**Center panel** is a live map of San Francisco showing the warehouse (blue), driver positions (green), and exception locations (red pins that pulse based on urgency). Clicking a pin shows the delivery details and resolution status.

**Right panel** is a scrolling activity feed showing every event as it is processed: timestamp, delivery ID, exception type, outcome (auto resolved or escalated), and processing time.

Events flow in real time: the event producer publishes exceptions to Redis, the dashboard backend consumes them through a background loop, runs each through the full LangGraph pipeline, and pushes the result to all connected browsers via WebSocket.

## How to Run

**Prerequisites:** Docker Desktop, Python 3.10+, Anthropic API key

```bash
# Install dependencies
pip install -r requirements.txt

# Set up environment variables
cp .env.example .env
# Edit .env with your ANTHROPIC_API_KEY and LANGSMITH_API_KEY

# Generate delivery manifest (uses public OSRM server)
python scripts/generate_manifest.py

# Start Redis
docker compose up -d

# Start the dashboard (consumes from Redis automatically)
uvicorn dashboard.app:app --port 8000

# Open http://localhost:8000 in browser

# Publish events to Redis (separate terminal)
python scripts/event_producer.py --flush --mode simulate --interval 5

# Run evaluation
python evals/run_eval.py --verbose
```
